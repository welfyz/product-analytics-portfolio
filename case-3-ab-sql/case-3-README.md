# Кейс 3. A/B-тест формы оплаты ЖКХ на SQL

Тот же кейс, что и в [кейсе 2](../case-2-ab-payment-form/), но все расчёты сделаны SQL-запросами. Результаты совпали с расчётом в Excel, это подтверждает обе версии.

**Данные:** учебное задание (A/B-тест формы оплаты с автозаполнением реквизитов, 1–30 апреля 2024). 1 500 пользователей, 2 660 платёжных попыток до очистки.
**Инструменты:** SQLite, DBeaver. CTE, оконные выражения не нужны, использованы `JOIN`, `CASE`, `COUNT(DISTINCT)`, `strftime`.

## Что сделано

1. Нашёл аномальные записи в сырых данных запросом (3 из 2 660): пользователь отсутствует в списке, платёж помечен чужой группой, интервал между шагами 3 и 4 равен 1 минуте.
2. Проверил очищенные данные: нет платежей без пользователя, нет дублей, нет несовпадения групп.
3. Посчитал воронку по шагам и конверсию шаг 1 → шаг 4 по людям.
4. Проверил результат по устройствам (парадокса Симпсона нет).
5. Посчитал конверсию между соседними шагами.
6. Проверил значимость z-тестом для двух долей (z² в SQL, так как в SQLite нет корня).

## Результат

| Группа | Открыли форму | Успешная оплата | Конверсия |
|---|---|---|---|
| A (старая форма) | 750 | 491 | 65,5% |
| B (новая форма) | 750 | 603 | 80,4% |

- Прирост: **+14,9 п.п.** (+22,8% относительно A).
- z = 6,51 (z² = 42,36), p < 0,001: разница не случайна.
- Новая форма лучше на обоих устройствах: Android 79,9% против 64,3%, iOS 80,8% против 66,9%.
- Сильнее всего разница на шаге «ввёл реквизиты → подтвердил платёж»: 81,5% → 91,1%.

## Как воспроизвести

1. Подготовить таблицы `users` и `payments` (очищенные данные, разделитель CSV `;`, пустые значения как NULL).
2. Импортировать их в базу SQLite (DBeaver: Import Data → CSV).
3. Для запроса 0 дополнительно импортировать сырые таблицы как `users_raw` и `payments_raw`.
4. Выполнить запросы из `queries.sql` по порядку.
